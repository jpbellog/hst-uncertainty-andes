# Fortran reference for the port validation

This folder contains the reference generated by compiling and running the original Fortran,
to validate the Python port against the actual code (not only against the papers).

## Compiling the Fortran

- Working compiler: gfortran 4.5.0 (distributed with "Force 2.0").
- The cygwin gfortran 7.4.0 does NOT work: it gives an internal compiler error (segfault) on
  the files with the `function/subroutine + common` pattern that mixes integers and doubles
  (`hellinger1.f`, `hellinger3.f`, `trikap.f`, `averotkap.f`, `teclib.f`). With gfortran
  4.5.0 they compile without problems.
- Flags: `-std=legacy -w`.

Commands (FC = path to gfortran 4.5.0):
```
"$FC" -std=legacy -w -o bin/hellinger1.exe  hellinger1.f dtrans.f numlib.f
"$FC" -std=legacy -w -o bin/add2.exe        add2.f dtrans.f numlib.f numlib2.f
# (add2.f is self-contained: it has its own inv/mul/matmul/trace/R1; do NOT link teclib)
```

### hellinger3 (triple junction)

`hellinger3.f` compiles with MinGW gfortran 6.3.0 (the MinGW `bin` folder must be on the
PATH so that `as`/`ld` are found):
```
export PATH="<MinGW>/bin:$PATH"
gfortran -std=legacy -w -o bin/hellinger3.exe hellinger3.f dtrans.f numlib.f bingham.f
```
Data and run (answers: file, guess 1->2, guess 1->3, amoeba again, level,
estimated kappa, and "n" to the plots):
```
python gen_reference_triple.py          # -> dataT.dat
printf 'dataT.dat\n33 -23 20\n-28 63 20\nn\n0.95\ny\nn\nn\nn\nn\n' | ./bin/hellinger3.exe > fitT_run.log
```
Comparison: `../validation/validate_triple_vs_fortran.py`.

## Files

- `gen_reference.py` : generates dataA.dat / dataB.dat (two independent rotations with
  unequal kappas: A with kappa~1, B with kappa~4).
- `dataA.dat`, `dataB.dat` : synthetic data in Hellinger format
  (line 1 = n sections; then `iside isect lat lon sd_km`).
- `fitA.txt`, `fitB.txt` : output of hellinger1.exe (rotation, kappa, df, H11.2, cov).
- `add2_reference.log` : output of add2.exe (combination with unequal kappas, Welch).
- Compiled executables: not included in this copy (Fortran sources of T. Chang, personal
  communication 2019). Only their outputs remain; the validation compares against them.

## How to regenerate

```
python gen_reference.py
printf 'dataA.dat\nfitA.txt\n20 -30 15\n0.1\nn\nn\n0.95\ny\n' | ./bin/hellinger1.exe
printf 'dataB.dat\nfitB.txt\n50 10 20\n0.1\nn\nn\n0.95\ny\n' | ./bin/hellinger1.exe
printf 'fitA.txt\ndataA.dat\nfitB.txt\ndataB.dat\n0.95\nout.txt\n' | ./bin/add2.exe > add2_reference.log
```
(The stdin sequence of hellinger1 is: data file, output file, "lat lon rho"
guess, search radius, n [no grid], n [no amoeba again], confidence level, y [estimated
kappa].)

## Validation result (validation/validate_vs_fortran.py)

- hellinger.py vs hellinger1.exe: identical rotation, identical kappa (dataA 0.77559,
  dataB 3.43945), exact df, H11.2 to ~1e-8 relative.
- welch_df vs add2.exe: capa=0.0362398, capc=0.0718547 (Johansen A,C that add2 computes from
  the raw data) -> E=3.0724795, Var=6.6510662, df=91.984, c=3.0056749,
  crit=c*F(3,df)=8.1262. All EXACT.

## Future use

`add2_reference.log` gives the capa/capc values that the Fortran computes from the raw
data (via the projections P0/P1). When the computation of the Johansen A,B,C from raw data
is implemented in Python (the last pending piece of the add2/add3 pipeline), it is
compared against these numbers (capa=0.0362398, capc=0.0718547 for this input).
